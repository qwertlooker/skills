# 文档与脚本内容审阅

用于接手已有适配、交付前自检和只读 review。这里规定审阅方法；内容标准分别在 [风格指南](style-guide.md)、[输出契约](output-contract.md) 和 [验证契约](validation-contract.md) 中维护。不要把语法、正则或 `--help` 通过当作本流程完成。

## 1. 确定覆盖范围并阅读

- 列出范围内的 README/其他用户说明、安装与数据准备、推理/服务、导出转换、评测/compare/benchmark 入口，以及它们使用的 helper、patch、配置和依赖文件。已有内部记录用于核实来源，不能替代读当前实现。
- 完整阅读范围内的用户说明和自有脚本；沿入口追到决定行为的函数、patch hunk 和配置。大型上游或 vendor 只读相关调用链，不要求全仓通读。搜索用来定位，不能仅凭命中片段或文件清单给出内容结论。
- “继续完成适配/整理交付”检查上述完整链路；窄范围修复只覆盖受影响链路及文档。记录排除项与理由。没有旧日志时从当前文件和可核实结果建立事实，不补造历史。

## 2. 逐项核对内容

评测或联合验收先从要发布的结论倒查原始结果：部署是否同一个、预期样本是否都在、比较器有没有读到这些结果。可以只在临时副本中改坏一个结果验证判定，再决定是否需要占卡。具体方法见[验证契约](validation-contract.md)。

按[审阅清单](review-checklist.md)核对本轮适用项，记录具体结论。交付所需但缺失的文件也列入核对范围。

将 README 的每条关键命令与参数解析、实际实现和输出逐一对应。代码可以解释行为，却不能单独证明实测结果；内部日志中的“通过”也不能证明当前代码仍正确。

## 3. 修复与复核

在已有内部记录或 review 报告中用紧凑表记录，不强制新建文件或填写 JSON：

| 对象/要求 | 内容证据 | 问题或保留理由 | 处理与复核 |
|---|---|---|---|
| README 评测命令 ↔ evaluate.py | README 小节；解析参数与汇总函数的文件/行 | 例如：说明使用了不存在的参数 | 修正文档或实现；记录 CLI/fixture 结果 |

表中示例不是待抄写结论。实际记录应含读过的路径/章节/函数或行号；同一调用链可以合并。标明符合、已修复、未解决、未验证或不适用及依据，不用“已检查全部”代替证据。

- 修复任务：修正范围内不符合要求的内容，保留有效说明和行为，不为统一外观整篇重写。只读任务：输出 finding、影响、证据和最小建议，不写回被审文件。
- 修改后重读相关章节、实现和 diff，确认文档、CLI、结果口径相符；再执行适用的自动检查、轻量失败路径验证与实际重放。运行失败时回到内容修复，不在检查输出处结束任务。
- README 排版或解释性文字变化通常不使数值证据失效；源码、依赖、数据、设备或评测逻辑变化按验证契约判断补验范围。需要独立候选时才按交付工作流组装。
- 缺 NPU、权重或数据时，完成可做的内容修复和宿主检查，并区分“内容已复核”与“尚未实测”。未读、未执行或过期证据不能标为通过。

## 4. 结束条件

范围内的适用项都有内容结论，发现的问题已修复并复核或明确列为剩余问题；自动检查与运行验证分别列出实际范围。只读审查允许有未解决 finding；修复任务不能把可直接修复的问题仅列为建议后停止。工具成功、打包成功或日志升级都不能单独满足结束条件。
