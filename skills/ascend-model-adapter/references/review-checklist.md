# 审阅清单（人工判断项）

用于接手已有适配、交付前自检和 PR 只读审阅。先固定本轮目标、源码版本或 PR head/base 与涉及目录，沿 README、实际入口、调用链和原始结果核对。窄范围修复只查受影响链路。多模型 PR 按模型目录查，共享文件单列。单样例以真实输入、实际执行设备和可检查输出为验收依据。训练、正式精度性能与上库按本轮要求核对。审阅步骤见[内容审阅](content-review.md)。

逐项给出**符合、已修复、未解决、未验证、不适用**之一，并附依据。当前证据证实问题仍存在时记为未解决，缺证据记为未验证，不适用附理由。打回信号用于定位问题，按对运行、结论或交付的实际影响判级。锚点、参数名、URL、占位符、lint 和快速检查单独记录实际覆盖范围。

## 1 口径一致

| 要回答的问题 | 打回信号 |
| --- | --- |
| README 承诺的参数、产物字段、支持范围和回退行为，能沿默认参数、生效配置和调用链找到对应实现吗？实现中影响使用或结果的行为有说明吗？ | CLI 接受参数但下游未使用，文档描述的分支不可达，示例字段与实际结果不符。 |
| 模型变体、版本、样本或配置数量及指标各有唯一的定义或数据来源吗？同一配置下的数值、单位和分母是否一致？ | 同一 split 出现不同样本数，同一配置新旧结果并存且都被当作当前值。 |
| patch 需求、实测设备和支持标记与交付文件及原始证据一致吗？需要记录的技术等级、上库就绪及已合入是否各有对应证据？ | 标记无需 patch，安装命令却必须应用它。用技术等级证明上库就绪，或用待合并 PR 证明已合入。 |

## 2 默认路径可执行

| 要回答的问题 | 打回信号 |
| --- | --- |
| 从 README 声明的起点和可用环境按顺序走，第一处阻断在哪里？执行目录、变量、路径和前置步骤是否闭合？ | 未取源码就应用 patch，改依赖声明的 patch 排在安装之后，同一变量混指源码和数据目录。 |
| 默认单样例所需源码、权重、配套文件和真实小输入，能通过声明的来源与命令获得吗？ | 必需输入标成可选，样例引用开发机已有文件，单样例意外要求全部评测数据。 |
| 默认入口的参数、加载路径与结果符合文档吗？正式评测另用配置时，能从评测命令查到生效值吗？ | 命令默认 batch 或上下文长度与声称可复现的结果不同，表中配置没有对应启动方法。 |
| 下载、解压、补丁或转换失败后，后续步骤会停在首个实际错误吗？声明的文件大小、哈希或记录数能复核吗？ | 中间步骤失败后沿用旧文件出数，校验比较的是另一版产物，体积或行数无出处。 |
| 使用者能通过产物或实际响应核实成功吗？服务就绪和请求结果是否来自本次实例？ | 只写“运行成功”，无输出位置或字段。新服务端口冲突，健康检查命中旧进程。 |

## 3 上游最小侵入

| 要回答的问题 | 打回信号 |
| --- | --- |
| 需要修改上游时，阻断是否发生在实际入口？固定版本的上游入口或配置能满足要求时，有没有多加替换层？ | 上游已有适用入口，仍运行期替换或复制实现。补丁混有无关重构。 |
| 源码补丁能在固定 revision 的干净副本试应用吗？确需改 `site-packages` 时，是否有单独补丁、准确定位和恢复方法？ | 应用目录或 `-p` 层级靠试错，残留备份被加载，应用后实际导入另一份包。 |
| 依赖冲突的根因与处理方式匹配吗？控制依赖解析时，是否按明确顺序保留镜像配套栈并安装业务依赖？上游元数据确有错误时，是否在源声明修正？ | `--no-deps` 跳过解析也漏装必需依赖。安装覆盖了 CANN 配套框架。错误的依赖声明继续生效。 |
| 保留的 shim 或运行期替换有固定版本依据吗？是否说清触发条件、被替换对象、失败方式和采用它的原因？ | 无条件 monkeypatch，匹配失败后静默改用另一版本或后端。 |

## 4 失败与实际运行可判定

| 要回答的问题 | 打回信号 |
| --- | --- |
| 成功、按协议跳过、续跑复用、部分失败和全部失败，能从退出码及汇总中区分吗？是否与实际执行及汇总的 ID、配置数相符？ | 子进程失败仍报通过，失败样本从分母消失，把未运行样本计入续跑成功数。 |
| 使用前是否真正检查必需依赖、文件和关键字段？对冲突参数、不可解释的 NaN/Inf、零有效比较是否按任务判定？合法空结果如何计分？ | `--help` 成功被当作依赖完整，输入损坏仍产出有效报告，空检测一律作为错误。 |
| 实际运行的设备、provider、dtype 和关键组件是否符合声明？允许的 CPU 前后处理及回退范围是否明确？ | 只凭已注册 CANN EP 判断 NPU 执行，实际核心节点落 CPU。图文请求返回文本，视觉特征未传入语言模型。 |
| 指定权重、关键 checkpoint 键和输入输出契约是否按实际加载与消费核对？ | checkpoint 能读取但关键键未加载，只消费 OM 第一项输出却承诺完整结果。 |
| 涉及训练或续训时，实际入口发生了预期参数更新吗？承诺续训时，能从落盘 checkpoint 恢复并再走一步吗？ | loss 有值但没有跨过梯度累积边界。只恢复权重，优化器或进度状态已重置。 |

## 5 指标带条件

| 要回答的问题 | 打回信号 |
| --- | --- |
| 精度用哪一份任务标签、官方 evaluator 或独立参照？权重、split、预后处理、解码、分母和公开基线同口径吗？ | 自算分数直接对标榜单。CPU 与 NPU 共用了改过的预处理，仅凭两端一致断言与上游等价。 |
| 变更过或首次接手的比较与汇总逻辑，能按原始评测样本清单核对覆盖吗？把结果改错后，正式判定入口会拒绝吗？阈值依据是什么？ | 参考端和候选端同时漏同一个 ID 仍通过，报告只打印差值，缺字段或判定失败仍给出通过结论。 |
| 声称同时满足质量与性能时，两份结果能绑定到同一实际部署吗？检查实际权重、实现或 OM、运行栈、硬件及生效的精度和解码设置。 | 精度来自 BF16，性能来自 INT8，却合并成一个部署结论。 |
| 调参与正式出数的入口、负载和计时边界能对应吗？是否写清真实或合成输入、输入输出规模、batch、并发或到达率、预热、重复次数和统计方式？ | 调参走空输入或跳过子模型，正式指标沿用其结论。首轮编译混入稳态，未同步的提交时间记为设备执行耗时。 |
| 在线延迟、吞吐和峰值显存能回到实际测量吗？延迟是否按请求统计，显存是否明确测量范围、统计字段与来源？ | 用总耗时除以请求数冒充 p95，忽略失败和超时。峰值显存引用的脚本未输出该字段。 |
| 已做的 CPU 验证和 NPU 实测分别支撑哪些结论？ | 以 CPU 功能或精度对照推算 NPU 吞吐或加速比，把单样例成功写成完整精度验收。 |

## 6 环境与公开边界

| 要回答的问题 | 打回信号 |
| --- | --- |
| 版本表能说明可复现的执行栈吗？是否交代实测硬件、镜像及所需的 CANN、Python、框架和后端版本，必要时解释 `+cpu`、post 号或设备映射？ | 仅写硬件和 CANN，遗漏实际加载的框架或后端。把共享卡的可用显存或本机测量值写成通用规格。 |
| 默认资源来源符合接收方环境吗？受限资源是否说明获取条件，离线准备和缺文件处理是否可执行？ | 公开用户第一步就需内网下载，离线缺权重分片时改从网络取另一份权重。 |
| README 保留了复现所需的版本、路径和限制吗？私有地址、主机名、作业号、存储路径、容器实例标识和内部验收信息是否留在内部记录？ | 使用命令依赖私有挂载，公开表中混入内部等级，或删除确实影响运行的限制。 |
| 内部记录能区分当前事实、失效证据和排障历史吗？现有记录能否直接补充？ | 每轮增加同职责的派生文档，新旧结论混在一起且无有效性标记。 |

## 7 证据可追溯、可重放

| 要回答的问题 | 打回信号 |
| --- | --- |
| 每项结论能找到对应版本的命令、环境和产物吗？需要正式证据时，能核对原始结果及其哈希吗？ | 命令使用已删除的参数或补丁，环境只写“本机”，产物已覆盖、缺失或无法核验。 |
| 证据类型与所证明的结论一致吗？源码、依赖、权重、评测或环境变化后，哪些证据仍有效、哪些需要重算或补测？ | 用 lint 或 dry run 证明 NPU 功能，用旧镜像的数字证明新部署，只凭新结果路径沿用旧结论。 |
| 正式比较报告是否标识评分时实际读到的输入，并给出任务判据？ | 结果路径被复用，旧比较报告仍用于证明新预测通过。 |
| 正式 ModelZoo 上库的审计与干净环境重放，是否都对应同一份候选组装报告？当前文件、哈希和执行位还能核对吗？ | 审计通过后换了候选文件，重放仍引用旧报告，或借用开发 checkout 的包和隐含资源。 |
| 目标仓 HEAD、目录与清单现状是否按当前查询确认？ModelZoo 的许可证、ModeList、自测试等是否按当前规范判断？涉及 PR 时，CI 和合入状态能对应当前 head 或目标提交吗？ | 用旧快照充当当前查询，引用旧 head 的 CI 判定本轮通过，或用新观察值静默替换冻结基线。 |

## 8 读者视角

| 要回答的问题 | 打回信号 |
| --- | --- |
| 各段能帮助读者判断是否适用，或完成安装、运行、评测和结果判断吗？ | 展开内部取证、调参流水或每轮验收过程，却遗漏实际操作和已知限制。 |
| 术语、模型名和路线名沿用上游或行业说法吗？表头或紧邻说明能交代指标来源、单位和共用条件吗？ | 把指标比对写成“对账”，用参数规模代替模型全名。数字分不清本次实测还是官方基线。 |
| 章节与工作仓约定或当前目标仓模板匹配吗？ModelZoo 样式差异能结合近期同任务、同路线条目解释吗？ | 有明确的贡献模板却缺所需小节，或为统一外观重写有效使用说明。 |
| 文档示例与脚本的实际摘要和产物一致吗？输出是否便于阅读和复制？ | 示意输出与真实字段不同，日志混入非 ASCII 装饰字符或大量调试输出。 |

## 9 交付文件与入口

| 要回答的问题 | 打回信号 |
| --- | --- |
| 新增脚本能说明独立职责吗？现有上游入口、官方 evaluator 或一条命令能否完成同一件事？ | 自造脚本只包装下载、拷贝或一次命令，两个同职责入口的默认参数和结果不同。 |
| 安装、推理和评测各有明确的默认入口吗？扫描、长稳等额外入口是否确有不同任务或约束？ | README 并列等价操作让读者选，主测、扫描和长稳重复实现同一调度和汇总。 |
| 依赖、配置、预后处理和评测逻辑是否尽量复用上游或项目已有实现？ | 自带一份上游依赖的复制品且版本不一致，另写 evaluator 但说不清差异。 |
| 独立候选及 README 能在接收方按声明的来源取得全部必需文件吗？验收证据的复核者能拿到所引用的材料吗？ | README 调用未交付的 helper，只靠私有目录中的测试脚本和结论证明可用。 |
| 交付树中的每个文件都服务于运行、评测、使用说明或目标仓要求吗？ | 把内部清单、组装报告、缓存、下载日志、wheel 或权重副本混入候选。 |

## 10 括号信息精简

| 要回答的问题 | 打回信号 |
| --- | --- |
| 说明文中的括号是否只承载单位或量纲、默认值与取值范围、必填或可选、可复制的示例？读者是否要据此操作或判断，删掉是否会用错？ | 括注对操作与判断均无影响，或仅解释写作及取证过程。 |
| 影响操作或结果理解的条件，是否写进命令、正文或表格？ | 命令写死某值，括号里提示实际应按表修改。把兼容性限制埋在括号里。 |
| 多个配置及取值能否拆成列？括号是否重复表头或嵌套多层？ | 在同一括号塞入多组值、来源和降批过程，或重复表头已说明的条件。 |
| 括号偏多时，逐处读后哪些信息该删除、写入正文或留在内部记录？ | “跨机复跑”“逐位一致”等取证与过程词反复补注，读者仍找不到实际判据。 |

## 使用方式

- 第一遍按 README 顺序审查第 1–9 节的适用项，重点走默认命令和交付入口。涉及正式验收时，从结论倒查判定、测量与原始产物。第二遍复读数字、术语与括号，确认精简后的命令与限制仍准确。
- 只读审阅给出可定位的问题、触发条件、影响、证据与最小修复建议。先读有副作用的入口，必要验证放入临时副本。修复任务直接处理范围内的问题，重读 diff 并重放受影响的操作。
- 结束时列明逐项人工结论及覆盖缺口、自动检查实际范围、已运行的验证及未执行原因。当前有效的原始证据可复用，缺设备或输入的项保留为未验证。
- 详细判据按需查阅[验证契约](validation-contract.md)、[输出契约](output-contract.md)、[风格指南](style-guide.md)、[补丁参考](patch-modification-patterns.md)与[ModelZoo 交付验收](modelzoo-delivery.md)。
