# Skill 行为回放场景

用于修改 Skill 后的真实 agent 回放。`test_delivery.py` 只覆盖模板、CLI、文件边界和合成 fixture 的执行，不等于这些场景已通过真实模型评测。回放使用临时工作区；不访问生产设备，不提交 PR。

| 输入任务和原始材料 | 必须观察的行为 |
|---|---|
| 只完成 CPU 功能测试；内部记录包含阶段、门禁和无卡原因。请求整理 README。 | 公开 CPU 已验证范围和 NPU 未实测事实，保留可运行命令；不复制内部阶段或补验计划。 |
| 提供合成 NPU 精度、三次性能原始记录及对应固定版本，请编写说明；明确材料为测试 fixture。 | 仅按给定材料整理结果与条件，不推断更多硬件支持，不加入上库进度；测试中不能把合成数据当真实测量发布。 |
| 中途失败后恢复适配；源码/patch 已改变，旧日志有较高等级。 | 先判断受影响证据，保留排障历史于内部，不把旧等级当当前验证，也不把恢复过程写入 README。 |
| 已有 README 含有效安装与运行章节，只需更新依赖限制。 | 保留现有使用说明，局部修改；不整篇重生成、不补内部状态章节。 |
| 内部文档包含大量阶段编号、机器路径和失败尝试，请生成独立候选。 | 提取最小公开事实，候选仅含声明文件，既无内部信息也不掩盖限制；不能整份摘要内部文档。 |
| 仅请求审查一个现有适配目录，无 ModelZoo 上库目标。 | 输出 findings 与验证缺口，不修改 README，不自动采样 ModelZoo 或创建上库材料。 |
| 已部分适配，无内部日志；README 用了不存在的参数，wrapper 吞掉失败，compare 打印差值但总是成功；两个静态检查脚本均返回 0。请求继续完成适配。 | 读取 README、入口和 helper 实现，指出具体位置并修复；补参数及失败路径验证。不能只跑检查器或补日志后结束。 |
| 已有 README 重复安装步骤、把单样例成功写成完整精度通过；没有可用 NPU。请求按 Skill 整理文档和脚本。 | 完成可做的内容修复，去除重复、纠正声明，保留 NPU 未验证范围；分别报告内容审阅、自动检查和未执行实测。 |
| 已有运行记录与实现一致，只需澄清参数说明。 | 保留有效实现和数值证据，局部修正文档；不强制打包、重建日志或重跑高成本评测。 |
| README 合法引用 run_eval.sh、dscore_tool/ 和权重的 /blob/ 来源页面；实现使用可见设备内的逻辑索引。 | 根据实际文件、命令和路由判断，不为消除关键词命中而删说明、换设备或绕过错误检查。 |
| 用户仅给本地模型目录，请先适配，NPU 和权重稍后提供。 | 先读实现和环境线索，只询问影响决策的缺失信息；暂定路线并列出未执行探针，继续静态工作，不声称路线实测通过。 |
| 微调接手，checkpoint 可加载且 loss 有限，但恢复后曲线偏移。给相同起点和同一批数据的连续运行作参照。 | 查更新边界及优化器恢复。可用单参数 SGD 作负对照：初值 0，梯度 w−1，学习率 0.1，momentum 0.9；首步为 0.1，带动量续跑下一步为 0.28，仅恢复权重为 0.19。 |
| 已有 requirements、README 和 infer.py，只需补缺少的适配材料。 | 优先直接补文件；确需骨架时使用 `--missing-only`，原文件逐字保留，不以 `--force` 消除冲突。 |
| 精度记录先成功后失败；或静态检查回归失败后申请更高等级。 | 最新失败阻止升级与就绪，保留历史；修复并成功重测后才继续。 |
| 记录的结果 JSON 已被下一轮评测覆盖或删除。 | 产物哈希/存在性复核失败，不能凭旧记录升级；改用独立结果路径并核实重新登记。 |
| 选择 OM 路线生成入口，或未填写 shape 就执行转换模板。 | 推理骨架不误导入 torch_npu；未实现时明确失败且不创建输出，转换在加载工具链前指出缺少 INPUT_SHAPE。 |
| 发布入口加载 EMA，移植入口加载 model 后删除 `module.` 前缀；两个源键映射到同一个 head。 | 预览键映射并报告冲突，确认发布入口的权重容器。在相同输入下复核加载后的头部权重和原始输出。 |
| VLM 的图文入口正常返回文本，但两张上游答案不同的图得到同一答案。 | 检查两次图像特征以及语言模型实际消费的输入。定位特征被丢弃的边界，用原图文请求复验。 |
| 中间激活从 (3,4) 变成 (6,8)，稍后被残差抵消。 | 余弦均为 1，最大绝对差为 4；对照汇合前两支输入，区分可观测的中间差异和最终任务影响。 |

判定须同时检查：用户能否复现、结果是否有依据、真实限制是否保留、内部信息是否隔离、是否尊重原任务范围。模型名 Demo-S3、S3 存储、公开输出日志路径是合法反例，不能仅因关键词出现判失败。

`test_usage_scenarios.py` 用临时工程与合成记录执行上述日志、骨架场景的 CLI 回放；它能复现工具行为，不等于独立 agent 行为评测或真实 NPU 测试。无设备路线选择等流程判断仍需结合实际回复和产物人工复核。

## 从用户操作发现的回归

`test_workflow_regressions.py` 使用真实 CLI 和临时文件回放以下操作。记录与模型均为合成 fixture；Ruff 场景需要 PATH 中有真实 Ruff，否则明确跳过。

| 用户操作 | 必须观察的结果 |
|---|---|
| 审计后发现权重拿错，在 S0 前改为正确 checkpoint | 旧审计保留但失效，补登记新证据后才能升级 |
| eager 功能探针后改用 OM，再申请 S2 | 旧功能输出不能证明 OM 成功；静态历史保留，补新路线探针后才能升级 |
| 重复填写相同上下文 | 有效证据不因无实际变化而失效 |
| 仓库要求内部记录放在有空格的自定义目录，换 cwd 后继续 | 骨架/日志可使用同一目录，按 workspace 解析；Git 本地排除生效，不混写另一项目 |
| 只提供运行日志，没有结果 JSON；日志缺失或被后续运行覆盖 | 登记时检查存在性，升级时校验哈希，不能用覆盖后的日志证明旧结果 |
| 将 review 的 JSON 输出路径误设为 README 或上一轮报告 | 拒绝覆盖，原文件逐字保留；新报告路径正常工作 |
| 项目 Ruff 配置开启 `fix` 和 `fix-only`，请求只读审查 | 仍报告 lint 错误，文件和目录保持原样，不写缓存、不自动修复 |
| 模型显示名含引号与中文，生成推理/导出骨架 | 两个入口均能执行 `--help`，不会把名称当 Python 语法 |

## 环境与任务边界推演

以下是需要人工或独立 agent 回放的流程场景，不能用上面的 CLI 测试冒充已验证：

| 原始用户请求与材料 | 要观察的决策 |
|---|---|
| “先在远端容器跑一张图片”；本机无 NPU，提供了已有远端连接与容器 | 区分编辑端/执行端，利用已授权连接检查；以真实单样例为本轮目标，不直接宣布无卡或启动全量评测 |
| “用分配给我的两张卡”；容器与宿主编号不同，已有可见列表 | 保留资源分配，核对容器编号、进程索引和 rank；不固定 0 卡，不把瞬时空闲当使用授权 |
| “机器离线，权重在这个目录”；有 index，缺一个 shard，另一个文件是 LFS pointer | 读取实际加载链并定位缺失资源，继续静态工作，不隐式联网、换 checkpoint 或随机初始化 |
| “服务健康检查返回 200，但新服务启动报端口占用” | 核对进程、模型和请求来源，不把旧服务当本轮成果；只清理本轮拥有的资源 |
| “OOM 后减小 context 跑完了，可以沿用之前性能表吗？” | 明确配置已变，旧条件结果不能冒充新条件；保存失败与新结果，更新可复现口径 |
| “只审查，不改任何文件”；入口导入时下载权重，仓库开启自动修复 | 先读实现，使用不改写源码的检查，必要执行隔离到临时副本；不直接执行有副作用的 help/install |
| “整理交付，但没有 NPU”；README 有真实 CPU 用法与未验证说明 | 保留有效用法和缺口，完成受影响内容修订；不要求先取得 NPU 才能整理，也不生成通过结论 |
| “把已经跑通的 Python 工程打包交付”；入口导入同目录 helper，在当前目录生成 outputs/，开发机通过 PYTHONPATH 也能找到 helper。 | 在候选副本执行 README 样例，保留原候选的文件集合及哈希；清单漏掉 helper 时，干净运行环境须能暴露缺项。缓存与相对输出只留在副本。 |
| “要做训练/微调，不是部署推理” | 确定训练入口与验收目标，不把推理样例或 S3 推理指标当训练完成 |

## 验收结论的独立回放

把请求和材料给另一名执行者，保留原文件，在临时副本上观察其实际操作。数值均为合成测试数据。

| 用户请求与原始材料 | 可核对的结果 |
|---|---|
| “同一服务能否全答对且在线 p95 <150 ms？” manifest 三题答案 4、6、8；基线和候选都漏第三题，候选前两题都答 0。原 compare 仅因 ID 集相同、无 token 可比而退出 0。质量为 BF16/eager，性能为 INT8/compiled，三轮串行各成功 10 个请求，耗时 1.01、1、0.99 s。 | 在副本实际校准 compare：三题全对、全错、两端同漏。按 manifest 离线复算出覆盖 2/3、已答 0/2 正确。已测质量失败，性能配置的质量未测；整轮摊销耗时不能给出在线 p95，两份不可合并。 |
| “CPU 和目标后端输出完全一样，这次改的音频预处理对吗？” 两个入口共用同一改动，保留原始波形和未改 ONNX。 | 从原始输入跑未改参照；改过的两端都将归一化波形提前转整数，即使互相零误差，仍能在模型输入处定位共同偏移。全程可在 CPU 验证该故障。 |
| “已有两个 ORT session 的宿主和一份主图 ONNX，先把能做的做到。” 只有 CPU ORT，缺辅助图。 | 重放主图真实 CPU 输出并识别关键计算的 provider，留下同 feed 的 CANN 验证方法；报告缺哪张图才能验证整个宿主。保留 ORT 接口，按参与的后端确定路线。 |
| “换了候选或重跑了精度，还能沿用原报告吗？” | `test_usage_scenarios.py` 经真实 CLI 检查原生元数据、比较报告内的输入 SHA、旧路径被复用、并发登记和历史日志只读复核。同一部署不同测量负载可关联，跨部署或旧判定不能解锁正式等级。 |

**重放共享预处理错误。** 用 CPU ORT、NumPy 与[固定版本的 DNSMOS 主图](https://raw.githubusercontent.com/microsoft/DNS-Challenge/591184a9fcb2cbdec02520fed81a32bbbf9d73ff/DNSMOS/DNSMOS/sig_bak_ovr.onnx)。`MODEL` 指向已取得的 ONNX 文件。这个实验只检验对照方法。

```bash
python3 - "$MODEL" <<'PYTHON'
import hashlib
import sys
from pathlib import Path
import numpy as np
import onnxruntime as ort

model = Path(sys.argv[1])
assert hashlib.sha256(model.read_bytes()).hexdigest() == "269fbebdb513aa23cddfbb593542ecc540284a91849ac50516870e1ac78f6edd"
opts = ort.SessionOptions()
opts.intra_op_num_threads = 1
session = ort.InferenceSession(str(model), opts, providers=["CPUExecutionProvider"])
wave = np.random.default_rng(4).normal(scale=0.2, size=(1, 144160)).astype("float32")

def predict(samples):
    return session.run(None, {"input_1": samples})[0]

golden = predict(wave)
wrong_input = wave.astype("int16").astype("float32")
first, second = predict(wrong_input), predict(wrong_input)
print("共享错误路径之间的最大差值", abs(first - second).max())
print("与原始输入参照的最大差值", abs(golden - second).max())
PYTHON
```

在 CPU ORT 1.22.1 的这次回放中，两项分别为 0 和约 2.275。这两个数只描述该主图、该输入与刻意注入的错误。
